# 自动推进守则（Autopilot）

用户已授权：无人监管下从当前进度一路推进到 Sprint 14（v0.4 打磨发布）。
本文件是自动化每一轮的唯一作业依据——每一轮都先读它，再决定做什么。

## 一、每轮固定动作（顺序不可变）

1. 读本文件 + `docs/decisions.md` + `排期-v0.1.md`，确认当前处在哪个 Sprint、该 Sprint 的完成定义。
2. 取**下一个未完成的最小交付单元**（一次只做一件，能一小时左右收口最好）。
3. 实现 → 自测 → 提交 → 版本 Alpha 进位。四件事缺一不可。
4. 把当轮结论写进 `docs/autopilot-log.md`（日期、做了什么、验证证据、下一步）。

## 二、完成的判定（Definition of Done，每轮都适用）

- `cargo check`/`cargo build` 通过，`cargo test` 全绿（新增逻辑必须带测试）。
- 前端改动必须用 Chrome 无头 `--dump-dom` 或截图确认没有 JS 报错（标题里出现 `ERR:` 即为失败）。
- 涉及真实窗口的改动，实机启动一次并截屏，确认没有视觉塌陷。
- 提交信息用 `type(scope): 摘要`，正文写清验证方式。
- 版本：每完成一个交付单元进一位 Alpha。写入用 `python scripts/set_version.py`，校验用 `python scripts/check_versions.py`。
- 未验证的能力必须在提交正文与日志里写明"未验证"，不许含糊成"已完成"。

## 三、绝对不能自作主张的事（遇到就停）

- 不擅自创建 GitHub 远端、不 push、不改仓库身份（等人拍板）。
- 不动用户的真实机器配置：不改系统环境变量、不装驱动、不删用户文件。
- 不为了"跑通"而降低安全标准（known_hosts 校验、密钥校验一律保留）。
- 不做排期外的功能扩张；临时想到的点子记进 `docs/backlog.md`，不顺手做。

## 四、需要人才有答案的阻塞（登记后跳过，继续别的单元）

1. 无可用 SSH 测试服务器/凭据 → 真实登录、PTY 交互、resize、tmux 全屏无法验证；只能做协议层与本地回环测试。
2. GitHub 远端与 PR 流程未定。
3. 预发布计数封顶规则（Alpha10 之后如何进位）用户未表态，按"满 10 进 patch、重新 Alpha1"执行并在日志留痕。
4. 图标已冻结，任何图标相关请求一律不做。

## 五、Sprint 4 之后的推荐顺序（按排期表）

| Sprint | 主题 | 关键交付 |
| --- | --- | --- |
| S4 | 打磨与可发布 | 设置页（主题/密度/字号）、错误提示统一、快捷键全表、打包配置、CHANGELOG |
| S5–S6 | 会话管理 | 会话保存/读取（本地 JSON）、分组、搜索、导入 Xshell/WinSCP 会话 |
| S7–S8 | 传输稳定性 | 断点续传、队列并发与限速、失败重试、中文路径与特殊字符 |
| S9–S10 | 终端体验 | 分屏、搜索、字号缩放、复制粘贴习惯对齐、tmux 兼容回归 |
| S11–S12 | 安全与凭据 | 口令本地加密存储、私钥口令解锁、主机指纹管理界面 |
| S13–S14 | 发布工程 | 安装包与签名、自动更新、文档站点、RC 回归与 v1.0.0 |

## 六、自动化节奏

由定时任务驱动（每轮一个最小单元，一天最多 4 轮）。每轮结束都提交，绝不留未提交的工作跨轮。
